## §4 两大已修病链 (闭环态)
### 4.1 #4 OOM 病链 (Patch A + B, 闭环 2026-07-25)
- **病链**: 超大 body → NVIDIA 400(glm-5.2 硬顶 202752 token) → omniroute 非终态拒而走 N-key round-robin fallback(auth.ts:1592 FALLBACK MODE 全跑) → 同体请求堆载累积 → heap OOM (dev 7key 1GB 默认堆崩 / 生产 25key 4GB 堆扛过空转终态拒)
- **Patch A** entrypoint:186 `NODE_OPTIONS="${NODE_OPTIONS:---max-old-space-size=4096}" node server.js &` — 4GB 堆回归, env 可覆
- **Patch B** gate.js 三 env + 中件: `CTX_GUARD_ENABLED`(默认开)/`CTX_MAX_BYTES=1500000`/`CTX_BYTES_PER_TOKEN=8` + `/v1` PSK后 proxy 前, POST + content-length>1.5MB → 413 `{type:"context_length_exceeded",est_tokens,limit_bytes}`. 仅判 content-length 不缓冲 body, SSE 流式不扰
- 8B/tok 实测标定(4 真实样本最小比率)退算单阈值: 1500000B÷8≈187500tok 距 200000 软限留 12500 余量
- KNOWN-LIMITATION: chunked 无 content-length 不拦(现有客户端均带); 比率<8 假想流由堆4096+fallback exhaustion 兜底
- 详 audit/2026-07-25-ctx-guard-oom-fix-landed.md

### 4.2 real_context 32K→200K + body 1→4MB (闭环 2026-07-24)
- 起源: 4.2.3 vs 4.3.2 两 boot 对比找"4.3.2 差"根因 = 32K override 砍 84% 触发压缩截断超时链 → 504/abort/eviction洪
- 三改: `real_context 32768→200000` / `body raw 1→4MB` / `echo 同步`
- 7 弹实证: A短200 / B 97K token / E 191K token 200 stop / F 1.05MB / G 3.719MB 入限 / H 3.719MB 504 边界(上游超时非咎)
- 模型名踩坑 `nvidia/z-ai/glm-5.2` 全名
- 详 audit/2026-07-24-realctx200k-body4mb-landed.md

## §5 一个未修当前 bug ★(架构调整须先解或绕)
### gc_stale_providers pipefail 杀 init (task5 C2 引入)
- **症状**: 每次 boot init 跑到 `[init] Keys: 7 registered` 后**静默崩**, `7 registered` 后全部段(gc_stale / Fetching provider IDs / Provider IDs / Resilience PATCH / combo upsert / model register / hf_snapshot) **永不执行**
- **真凶**: init-nim-keys.sh:2 `set -eo pipefail` + 行 ~157 `_DEL_JSON=$(jq... | grep -v '^$' | jq -R . | jq -s 'unique')`. 无待删态(fresh R2 空库首发, 7 连接全 nim-01..07 无僵尸无重复)时 jq 输出空 → `grep -v '^$'` 对空输入返 **rc=1**(无匹配行) → **pipefail 致 pipeline rc=1** → **set -e 杀 init 进程**
- **合成验复现**(本地两场景):
  - 场景1 无待删 + `set -eo pipefail`: 调用后无 echo, 退 rc=1 ✅ 复现
  - 场景1 无待删 + 修法(set +eo pipefail 抬门 + ${_DEL_JSON:-[]} 兜底): echo "无待删连接 (当前 NIM_KEYS=7, 增量幂等)" rc=0 ✅
  - 场景2 僵尸 nim-09+重复 nim-01 + 修法: echo "删除 2 个僵尸/重复" rc=0 ✅
- **修法(已验未落源)**: `_DEL_JSON` 赋值包 `set +eo pipefail` 抬门 + 赋值后 `${_DEL_JSON:-[]}` 兜底 + `set -eo pipefail` 复原
- **后果**: boot 看似健康 7 registered, 实际**整个池没建**(combos/providerIDs/Resilience/override/modelRegister 全没跑). 比"显式崩"更隐蔽
- **架构痛点暴露**: `set -eo pipefail` 配 jq/grep pipeline 组合, **空输入 grep 返 rc=1 即杀** 是 bash 语义地雷. 全 init 大量 pipeline 类似模式, 类似 bug 可能潜伏多处

## §9 架构痛点汇总 (重构候选面, 供 K3 讨论)
### 痛点1: init 1046 行单体, set -eo pipefail + jq/grep pipeline 地雷
- 20 函数挤一文件, 主执行段(行 515-1046)线性长流, 任一 jq/grep pipeline 空输入即 pipefail 杀(Set 或 调用点散)
- **重构候选**: 拆模块(model/tier/ratelimit/combo/gc/snapshot 各一文件) + pipeline 统一 `{ ... ; } 2>/dev/null || true` 容错包 + 空输入专门分支 + 退出码显式检测替代 set -e 全局
- 或: 保留 set -e 但全 jq/grep pipeline 加 `|| true` 守门

### 痛点2: 双部署改动需两套镜像重建
- 改上游 src = 生产 fork 官方镜像 + dev 重推 GHCR BASE_IMAGE = 双 Rebuild 每版重移植, 性价比低
- **当前回避**: §5 改 gate 自有代码走 Dataset 零 Rebuild, 生产 gate 圣上手其 http-proxy-middleware 版
- **重构候选**: (a) 两部署统一基镜像(GHCR 多 tag: dev/prod 各一), 改 src 只需重建多 tag; (b) 把更多防护下沉 gate 自有代码(不依赖 upstream 改)

### 痛点3: HF 免费层硬限 (build 冻 / 48h 休眠丢数据 / 2vCPU)
- 7/16 后密集 push 冻 build: 三层解耦绕(逻辑层 Dataset push+Restart)
- ephemeral 48h 休眠: R2+Litestream 副本补, 但每次冷启 restore + init 全跑有窗口
- **重构候选**: (a) 留 R2 默认主路径不变; (b) 探 GHCR 多 tag 减 Rebuild 频; (c) init 幂等性加强(Restart A/B 模式已有, 但 C2 bug 暴露幂等路径未测)

### 痛点4: 配置/状态多源易漂移
- SQLite(运行态) + R2(Litestream WAL) + Dataset(逻辑层 5件) + Environment Variables(Space Secrets) + upstream src(双版本) 五源
- CLAUDE.md §4 SSOT 文档链入口 + §5 双版本对照纪律已立, 但改动易留 drift(历史: patch-gate 丢 / api-keys schema 漂 / export-json 修)
- **重构候选**: 单一 SSOT 工具(upstream_check.sh 已制度化抓 Dockerfile 关键行)扩至全逻辑层 drift 检测

### 痛点5: 凭据/护栏手工条目多, 易漏
- .claude/settings.json deny16/ask2 + secret-scan hook + pre-commit 已立, 但 ~/.omn_env 凭禁触靠人记
- GHCR PAT classic + HF dataset-write token 各入 omn-secrets 600
- **重构候选**: 扩 secret-scan 覆盖更多密钥形态, env 占位自动化 checklist 工具
