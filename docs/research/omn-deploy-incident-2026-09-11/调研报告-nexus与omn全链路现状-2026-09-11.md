## 一、omn 网关：部署链断在"硬编码清单"

### 1.1 事实链（逐条可复核）

1. **真源完整**：`nexus.zen/omn` 的 `logic/` 目录共 9 项（8 文件 + `tests/`）：
   `entrypoint.sh` `gate.js` `helper.sh` `init-nim-keys.sh` `omn_redact.py` `omn_scheduler.py` `package.json` **`policy-guard.js`** + `tests/`
2. **gate 依赖它**：`logic/gate.js:22` → `const policyGuard = require('./policy-guard.js');`（顶层加载，非惰性）
3. **三处硬编码清单都只有 8 项，且都不含 `policy-guard.js`**：
   - `space/start.sh:60-61`（boot 时从 Bucket 拉哪些文件）
   - `.github/workflows/sync-logic-xnexus.yml:58-59`（CI 上传哪些文件）
   - `.github/workflows/sync-logic-xnexus.yml:104-105`（CI 回读校验哪些文件）
   - 其中第 2、3 处是**同一个 workflow**，所以"上传漏了"和"校验也漏了"同时成立 → CI 永远绿。
4. **注释与代码自相矛盾**：`space/start.sh:52` 注释写"拉 manifest **+ 9 件**（8 业务 + flaretunnel 二进制）"，但 `:60-61` 实际只列了 **8 项**（7 个来自 `logic/` + 1 个 flaretunnel）。
   → **`policy-guard.js` 正是那个"被注释算进去、被代码漏掉"的第 8 件业务文件。**
5. **运行期证据**：`gate-stderr.log` 报 `Cannot find module './policy-guard.js'` → `entrypoint.sh:482` 以 STRICT 方式跑 gate，gate 死亡视为致命 → 全量拆除 → HF 重启循环（约 17s 一轮）。
6. **预检盲区**：`entrypoint.sh:434-435` 只检查 `/logic/gate.js` 是否存在，**不检查 gate 的相对依赖**。所以缺 `policy-guard.js` 时预检照样放行。

### 1.2 为什么"CI 全绿"却漏了

`sync-logic-xnexus.yml` 的校验逻辑是「**对清单里的文件**逐个比对 sha256」。清单本身漏了文件 → 校验范围就漏了 → 报"8 件 sha256 全对"。
这是典型的**清单型 CI 的自我确认偏差**：CI 证明的是"我上传的东西是对的"，不是"该上传的东西都在"。

### 1.3 修复（三步，缺一不可）

| # | 动作 | 位置 |
|---|---|---|
| 1 | 三处清单各加一项 `policy-guard.js`（8 → 9 项） | `space/start.sh:60`、`sync-logic-xnexus.yml:58`、`sync-logic-xnexus.yml:104` |
| 2 | 触发 CI 重跑（`logic/**` 有改动即自动跑），Bucket 得到 9 件 + 新 `manifest.json` | GitHub Actions（sync-logic-xnexus） |
| 3 | **人工重启 Space**（三层解耦：推 Bucket 不触 rebuild） | HF Space `xnexus/o` |

### 1.4 建议的加固（防复发）

- **预检升级**：`entrypoint.sh` 的预检从"gate.js 在不在"升级为"gate.js 的所有相对 `require()` 目标在不在"。
  → 已产出 `n-omn-gate-deps-check.sh`（扫描 gate.js 的 `require('./x')`，缺件即 FATAL），可直接挂到 `entrypoint.sh:434` 那块。
- **校验清单改为派生而非手写**：把 `files = [...]` 换成"`logic/` 目录实际内容 − 白名单（tests/ 等）"。手写清单必然再次漂移。
- 备注：`logic/tests/policy-guard.test.js` 已在 git，但**不应**进 Bucket（运行时不需要）。

## 二、nexus 双仓同步：一个从未生效的"假绿"镜像

### 2.1 事实链

1. CNB 侧 `.cnb.yml`（commit `55c1b29` 时点）有两个触发：`main.push` 与 `crontab: */15 * * * *`，两者都执行"`git push github HEAD:main --force`"。
2. 脚本开头是软跳过：`if [ -z "${GITHUB_TOKEN:-}" ]; then echo "⚠️ …跳过…"; exit 0; fi`
3. **构建日志实读**（构建号 `cnb-4pg-1k273dj68`，2026-09-11 10:05:51，CNB main HEAD）：
   ```
   ⚠️ 未检测到 GITHUB_TOKEN，跳过本次镜像（请在 CNB 项目设置中配置）。
   exit code: 0, signal: 0
   ```
   该构建在列表中的状态 = **success**。
4. **cron 同样空转**：近 5 天构建事件统计 —— push 104 次、`crontab: */15` 64 次、npc 类 87 次。cron 每次都执行到同一个软跳过分支。
5. **GitHub 实际状态**（GitHub API 实读 `i3t2y/nexus`）：
   - 最新提交 `4601942`（2026-09-07T18:14Z，author=committer=`zen`）= **直接在 GitHub 上提交的**
   - 根目录**有 `eval/`**（14 项左右）
   - 根目录**无 `.cnb.yml`**
6. **两仓已分叉**：
   - CNB main 领先本地旧快照约 50 个提交，最新 `55c1b29`（2026-09-11T10:05）
   - GitHub 有若干 CNB 没有的提交（`4601942`、`c89f778`、`7090557`、`f27c69c`、`30b4e88`…）
   - 交集之外各自都有独有历史 → **不是"落后"，是"分叉"**

### 2.2 风险（按严重度）

| 级别 | 风险 | 说明 |
|---|---|---|
| 🔴 高 | **一旦补上 token，cron 会在 15 分钟内 force-push** | 现行脚本是**整树 force 覆盖**：会同时抹掉 GitHub 的 `eval/`（答案键真源）**和** GitHub 独有的那些提交 |
| 🔴 高 | **假绿掩盖了 3 天的失同步** | `exit 0` 让"未配置"和"推送成功"在列表里长得一模一样，无人察觉 |
| 🟠 中 | 两仓分叉无收敛机制 | 现行 `--force` 语义是"CNB 无条件覆盖 GitHub"，但 GitHub 侧已有人（zen / hermes-bot）直接提交 |

### 2.3 修复顺序（**顺序不能颠倒**）

1. **先**把 `.cnb.yml` 改成 overlay 语义（CNB 树覆盖 GitHub，但保留 GitHub 独有的 `eval/`），已写好并在本地端到端演练通过（`_sync_dryrun/`）。
2. **再**处理分叉：把 GitHub 独有的提交内容回灌 CNB，或显式确认放弃（二选一，需人裁决）。
3. **最后**才配 `GITHUB_TOKEN` + `GITHUB_USER`（CNB 项目 → 流水线 → 变量，勾"保密"）。
4. 顺手把软跳过改成硬失败（或至少 `exit 1`），消灭假绿。
