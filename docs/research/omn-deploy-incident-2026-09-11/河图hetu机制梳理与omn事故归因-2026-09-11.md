# 河图（hetu）机制梳理 · 与本次 omn 事故的归因（2026-09-11）

> 调研方式：CNB OpenAPI 实读 `nexus.zen/nexus` 的 `docs/self-improvement/` 全量 + `nexus.zen/omn` 的 PR#13 正文/评论 + GitHub `i3t2y/n-omn` 实读 + HF workflow 内容。
> 结论：**事故不是"代码写错了"，而是河图闭环缺了"部署耦合"这一整段。** 下面逐条给证据。

---

## 〇、一句话归因

河图把 **merge 当作"上线"的终点**。但 omn 的实际"上线"是四段：

```
merge → ① 改三处部署清单（若增删 logic 文件）→ ② CI 推 Bucket → ③ 人工重启 Space
```

本次只完成了 `merge` + `②`（而且 ② 只推了清单里的 8 件）。
**① 没人做，③ 做了但推的是残缺件** → gate 加载即崩。

而且这不是"忘了"——PR#13 的正文与最终评论里，NPC **两次明确声明"未改部署文件"**，是一次**合规的、被系统接受的**声明。系统里没有任何规则要求它改。

---

## 一、河图是什么（实读纪要）

### 1.1 三要素

| 河图中 | 本栈对应 |
|---|---|
| **图**（自然涌现） | CodeBuddy 的 PR / diff |
| **则**（演化律） | eval-gate 评分 + 白名单 + 禁线 |
| **圣人**（则之） | hermes 自动 merge / 驳回 |

### 1.2 角色（`河图-规矩.md` 〇章）

- **Zen（主）**：唯一裁决者，拍板规矩、审 code/测量仪 PR、可推翻任何一条。
- **hermes（主脑）**：常驻，派单、评审、按规矩直合 docs、管 eval 栈、记账。
- **CodeBuddy（NPC）**：干活的。只看 nexus 仓 + issue/PR；**永远看不到 eval 集、token**。

### 1.3 运行时刻表（生产）

- cron `job_id=7ba58d1d571b`，每 10 分钟 `gate.py` 扫 `nexus` / `npc-lab` 的 open PR。
- 对 NPC 的 PR 跑评测：8 题、`sensenova-6.8-flash-lite`；通过 baseline → 自动 merge（白名单内）+ squash。
- 不达标 → 召唤 CodeBuddy 返工，**每 PR 上限 1 次**；评分卡永远进 PR 评论。
- 自称动了测量仪却测不出幻觉的 PR → 跳过，人工裁决。

### 1.4 评审口径（`河图-规矩.md` 三章）

- `fused = 0.4×rule + 0.6×judge`；judge 挂则自动退 rule。
- 放行线：docs ≥ baseline−0.05；code ≥ baseline−0.10。当前 baseline(train) = 0.87。
- 幻觉扫描：声称动测量仪 / 自吹自擂 / 根目录误放 → 直接 flag，不进 fused。
- **五个评分维度：correctness / completeness / adherence / reproducibility / efficiency** ← 记住这五个，后面是重点。

### 1.5 递归闭环（`河图-规矩.md` 四章，原文）

> idea → issue 派单 → NPC 交 PR → gate 审 → 过则 docs 直合 / code 报 Zen → 结果入 cases_pool → baseline 定期重采样刷新。

**注意这里没有"部署/上线"这一步。** 后面会看到这就是根因。

### 1.6 立项五字段（`experiment-protocol.md`，任一为空 = 拒收）

`假设 hypothesis` / `基线 baseline` / `成功判据 success criteria` / `测量方法 measurement` / **`回滚方案 rollback`**

其中回滚方案的定义原文是：

> 失败后怎么退：**git revert 哪几个 commit**，或人工关闭哪个 PR。

→ **只到 git 层，覆盖不到"部署通道"（Bucket / manifest / Space 运行态）。**

### 1.7 merge 分级（`merge-原则.md`）

| PR 类型 | 谁 merge |
|---|---|
| docs-only（`docs/**`，不动测量仪/脚本） | hermes 直合（API squash） |
| `scripts/**` / `.py` / `.sh` | Zen 必审 |
| 动测量仪（`/data/.hermes/eval/*`） | Zen 必审 |
| 凭证 / secret | 拒绝 |

### 1.8 红线（`河图-规矩.md` 一章）

1. 凭证永不入 git。
2. eval 集只在 `/data/.hermes/eval/`，不进 git/CNB、不给 NPC 看。
3. NPC **不开 token、不动 `.cnb*`、不动 `.env*`、不在 `scripts/` 外放代码**。
4. 生产仓（nexus）`scripts/` / `.cnb.yml` / 测量仪类 PR 必须 Zen 亲审；docs-only 可 hermes 直合。

### 1.9 扩仓到 omn（2026-09-10，`ideas/2026-09-10-gate-add-omn.md`）

- 起因：omn 仓已镜像至 CNB、接入河图（CodeBuddy 已交首份诊断报告 PR#2 并 merge）。
- 动作：`gate.py` 的 `REPO_WHITELIST` 加 `nexus.zen/omn`，使 omn 的 PR 也走 fused 判定。
- 原文风险自述：

> omn 仓 PR 可能涉及生产网关逻辑（`logic/gate.js` 等），但 **omn 仓的 merge 永远人工，gate 只给评分+评论，不改产**。

→ **河图在扩仓时，明确把自己在 omn 上的职责限定为"评分+评论"，把"生效"整段留给了人——但没有留下任何人的清单。**

## 三、契约缺口（四处，精确定位）

| # | 缺口 | 位置与证据 |
|---|---|---|
| G1 | **五字段没有"部署影响面"** | `experiment-protocol.md` 只有 假设/基线/判据/测量/回滚；且「回滚方案」的定义只到 `git revert`，**覆盖不到 Bucket/Space** |
| G2 | **必人审清单没列部署耦合文件** | `merge-原则.md` 只列 `scripts/**` / `.py` / `.sh` / 测量仪；**`space/**` 与 `.github/workflows/**` 不在任何一行**。PR#13 动的是 `logic/*.js`（连 `.sh`/`.py` 都不算）→ 分级表里它甚至不触发"Zen 必审" |
| G3 | **闭环四段里没有"上线"** | `河图-规矩.md` 四章闭环止于 `merge`；`河图-hetu.md` 说"立项→假设→**上线**→测量→归档"，但"上线"在规章里没有对应动作 |
| G4 | **发布检查单过期且缺项** | `docs/ops/release-checklist.md` 全篇 **A/B/C/D/M 五段没有一段**涉及"logic 文件增删 → 部署清单/start.sh/manifest 同步"；且 C1/C2 仍在写 litestream/R2（CLAUDE.md v4 已宣告该链 2026-09-05 全废）→ **检查单本身已失真** |

### 补充：omn 的"生效"路径本身是半自动的

- **自动**：GitHub `origin`（`i3t2y/n-omn`）→ Actions → Bucket。
- **手工**：Bucket → Space 生效，必须**人工 `Space Settings → Restart`**（三层解耦，推 Bucket 不触 rebuild）。
- **反向同步**：CNB 是 omn 的镜像（`agent-instructions.md` 载明"镜像自 GitHub `i3t2y/n-omn`"）；CNB 上 merge 的结果要回到 GitHub 才能触发 Actions——这一步在 `.cnb.yml` 里**没有对应流水线**，属于流程外操作。

→ 也就是说：omn 的"merge → 生效"之间**至少有两处依赖人记得做的动作**，而河图闭环里没有任何一处记录它们。

## 四、结论

1. **河图本身没坏**：它按设计工作——评分、判退、返工、放行，PR#13 还真的靠 judge 的 0.440 逼出了 4 处真退化修复（这是它的功劳，不是它的错）。
2. **坏的是闭环的边界**：河图的标的只有"代码/文档质量"，而 omn 这类**有独立部署通道**的仓，"merge"只是中点。缺的那一段（部署耦合）**没有角色、没有字段、没有清单、没有检查**。
3. **特别值得注意**：NPC 的声明是**诚实的**。它没撒谎、也没偷偷做事。这说明该缺口不会被"加强 AI 自律"修掉——**它只能靠把"部署影响面"写成硬字段/硬检查来修**。

## 五、修法建议（分三层，按投入递增）

### 立刻（治本次）
1. 三处清单各加 `policy-guard.js`：`space/start.sh:60`、`.github/workflows/sync-logic-xnexus.yml:58` 与 `:104`（GitHub 侧同改）。
2. 触发 sync-logic CI 重跑 → Bucket 得 9 件 + 新 manifest。
3. **人工重启 Space** → 过 `release-checklist` A 段（boot 九段 + init rc=0）。

### 短期（防复发，仍低成本）
4. **清单派生化**：把 `files = [...]` 换成"`logic/` 目录实读 − 白名单（`tests/` 等）"，手写清单必然再漂移。
5. **CI 加反向断言**：先扫 `logic/` 实际文件集，与上传清单取差集，**有差即红**（现在的 CI 只证明"清单内文件对"，证明不了"文件都在"）。
6. **预检升级**：`entrypoint.sh:434` 从"查 gate.js 在不在"升级为"查 gate.js 的全部相对 `require()` 目标在不在"（已备 `n-omn-gate-deps-check.sh`）。
7. **release-checklist 补一段「部署耦合」**（logic 文件增删时逐条打勾），顺手删掉已废弃的 litestream/R2 条目。

### 结构（治本，须人裁决）
8. **五字段加第六字段「部署影响面 deploy impact」**：写明"是否增删 `logic/` 文件 / 是否需改部署清单 / 是否需重启 / 回滚是否覆盖部署通道"。空 = 拒收，与其余五字段同权。
9. **merge 分级表加一行**：`space/**`、`.github/workflows/**`、`logic/**` 的**新增/删除文件** → Zen 必审（或至少强制人工确认部署影响面）。
10. **闭环四段改成五段**：`merge → 部署耦合 → 验证 → 归档`，并明确"未过部署耦合 = 未上线"，杜绝"merge 即上线"的默认假设。
