# k3 故障诊断报告 — 2026-09-09 凌晨

> 性质: 只读分析归档 (不动 logic/ 任何代码)。
> 事由: kimi-k3 经 omn 网关调用异常, 三层证据指向"上游拒 + 本侧放大"叠加。
> 证据来源: 生产 boot/运行日志 (2026-09-09 凌晨) + 本仓代码实读 + upstream 3.8.50 只读树。
> 结论口径: 只写现象/层位/机制, 不含原始 token、完整对话与密钥。

---

## 一、三层证据 (状态码 / 耗时)

| 层 | 现象 | 状态码 | 耗时 | 指向 |
|---|---|---|---|---|
| L1 上游快速拒 | 一批请求被秒拒 (conv_71def8ee, Ti:0 TO:0) | 400 | 300-474ms | NIM 服务/账号侧 |
| L2 硬超时 | 失败请求耗时高度一致, 20+ key 逐个重放 | 502 | 240.1-242.6s | 本侧 fallback 设计 |
| L3 假成功 | 固定 query 每 11min 复现, TPS 上千 | 200 | 1-5ms | 语义缓存命中 (探活假象) |

三条证据是三个独立机制在同一时段并发: L1 上游真故障, L2 本侧把上游慢放大成风暴, L3 观测面被缓存污染。

---

## 二、层位归因 (NIM vs omn)

| 现象 | NIM | omn | 判据 |
|---|---|---|---|
| 400 / 300-474ms 批量 | ✅ 主责 | — | 500ms 内即返回结构体, 非超时非网络, 属服务端准入/账号侧拒绝 |
| 502 / 240.1-242.6s 全等耗时 | 触发源 | ✅ 主责 | 呈平台式掐断, 非本侧单窗; 同请求逐 key 重放为本侧行为 |
| 200 / 1-5ms 高频 | — | ✅ 全责 | 上游不可能 1ms 出结果, 命中语义缓存直回 |
| 20+ key 轮询同一请求 | — | ✅ 全责 | 上游只看到独立小请求, 不感知轮询 |

**一句话**: NIM 端确实病了 (快速拒 + 长请求掐断), 但把它轰成 80 分钟空转的是本侧 fallback 无输出就跨 key 死磕的策略。**两个问题的乘积, 不是和。**

---

## 三、fallback 放大链条 (本侧机制)

```
客户端一次 k3 长请求
   │
   ├─ 目标 A (连接 ca-01) ── 上游不吐首个内容事件
   │      └─ 触发 stream readiness 超时 → 该 connection 标记耗尽
   │         (未吐内容的 connection 级失败, 计入本请求 skip 集)
   │
   ├─ 目标 B (连接 ca-02) ── 同上, 再等一轮超时
   ├─ 目标 C ...                                    ← 逐 key 重放同一 body
   │
   └─ 目标 T (第 20+ 个连接) ── 最终 502
         单请求累计 ≫ 上游单次超时窗 ≫ 客户端耐心
```

放大倍率 ≈ (单次上游等待 × 重放连接数)。本侧机制要点 (upstream 3.8.50 只读树实证):

1. **combo 逐目标重放**: `combo/comboConfig.ts` 默认 `maxGlobalAttempts=30` (硬上限 200,
   `combo/comboPredicates.ts:100`), `maxRetries=1`; 单 target 失败即换下一个 → 单请求 ≈30 次重放预算。
2. **连接级失败被"跳过剩余同连接目标"**: `combo/targetExhaustion.ts:38` `CONNECTION_LEVEL_ERROR_STATUSES`
   含 408/500/502/503/504/524。无输出→超时被判连接级失败, 记入 `exhaustedConnections`,
   剩余目标改走下一个连接 → **同一份 body 挨个 key 重跑**。
3. **单请求总预算缺省**: `comboConfig.ts:180` `comboTimeoutMs: 0` (= 不限总墙钟), 仅靠
   `COMBO_LOOP_SAFETY_TIMEOUT_MS=10min` 兜底 (`combo/comboPredicates.ts:25`)。
   → 30 次 × 每次真跑到上限 = 长窗空转的算术基础。
4. **上游单次等待窗**: 上游 `DEFAULT_STREAM_READINESS_TIMEOUT_MS=80_000` /
   `DEFAULT_STREAM_READINESS_MAX_TIMEOUT_MS=180_000` (`src/shared/utils/runtimeTimeouts.ts`);
   `logic/entrypoint.sh` 已把 `STREAM_READINESS_TIMEOUT_MS` 抬到 180s (为长思考首 token 静默)。
   **单次等待 180s × 30 次重放** = 600s 级空转的算术来源。

## 四、假成功 200 的来源

- 上游 3.8.50 `src/lib/semanticCache.ts`: 缓存键 = SHA-256(model + 归一化 messages + temperature + top_p),
  `isCacheableForRead` **要求显式 `temperature: 0`** 才可命中/写入 (省略 temperature 不缓存)。
- 故 "1-5ms 200" 的必要条件 = 固定 query + 显式 temperature=0; 探活/健康检查流正满足 → 稳定周期复现。
- **判读**: 这批 200 不代表 k3 健康 — 同期真实长链全是 240s 502 / 300-474ms 400。
  不剔除缓存命中样本, 监控只会得出"上游时好时坏"的错误结论。
- 旁证: 上游对 200 后空 SSE 流另有 EARLY_EOF 判据 (`comboPredicates.ts`), 缓存直回/真空答/真上游 200 须分开计数。

## 五、改进方向 (只列方向, 不写实现)

1. **单请求总预算**: 给 k3 类长思考组合设 combo 级总墙钟预算, 让"最多等多久"由策略定, 而非由池大小定。
2. **重放去重**: 同一 body 在同一上游症状 (无输出/同状态码) 下, 不应对每个连接全额重放;
   可考虑症状级短路 + 指纹去重 (本仓 `tools/patches/p0/retry-after` 的去重接口已有雏形)。
3. **上游无输出即快速终止**: 区分"上游明确拒绝 (400)"与"上游沉默", 沉默类应尽早终止而非等满窗。
4. **观测分层**: 200 计数必须拆分缓存命中 / 真上游 200 / 空答 200, 否则告警与报表继续被假成功掩盖。
5. **告警按请求口径**: 把"每请求 30 次重放"折算成**请求级** P99, 比单调用口径更能暴露风暴。
6. **止损闸**: 上游批量快速拒时触发按 provider 的短时熔断, 不再继续按连接轮询。
7. **日志口径统一**: 240s 级耗时须标"等待窗超时"而非笼统 502, 一眼分清上游掐断与本侧等满。

---

## 六、结论

- **k3 服务器侧确有问题**: 400 快速拒 (准入/账号侧) + 长请求被掐断。
- **轰成风暴的是本侧 fallback 策略**: 无输出就跨 key 死磕, 把上游的"慢/拒"放大成 80 分钟级空转。
- **两者是乘积关系**: 上游不病 → 本侧无重放机会; 本侧不放大 → 上游故障只表现为单次失败。
- **假成功 200 是观测噪声**: 语义缓存命中 (需显式 temperature=0), 不构成 k3 可用性证据。
