### 事实 1【新增 · 高危】河图的评测集，连标准答案一起，公开在 GitHub 上

**实测**（匿名、无 token）：

```

```

两份 JSON 里是**完整的 prompt + assertions + 每项 weight + banned_patterns**。任何人都能匿名读到。

**这与你们自己写的规矩直接冲突**：

- `docs/self-improvement/河图-规矩.md:10`：
  > **CodeBuddy(NPC)**：干活的。只看 nexus 仓 + issue/PR；**永远看不到 eval 集**、token、规矩之外的世界。
- `eval/README.md`：
  > `heldout.json` —— 4 例 held-out，**全程不参与优化**，仅终验（**防过拟合**）。

**影响**：河图整个"防过拟合保险丝"已失效。规则说 NPC"只看 nexus 仓"——而**就叫 `nexus` 的那个公开仓里，正躺着全部答案**。公开仓里的 heldout，不配叫 heldout。已产出的任何分数，严格讲都不可信。

**⚠️ 与 P1 的致命耦合**：修复镜像时，
- 若按**现在**的整树 `--force` → `eval/` 被删，**歪打正着堵了漏**；
- 若按**正确的** overlay（保留 `eval/`）→ **把漏洞永久固化**。

所以：`eval/` 的正确归属不是"留在 GitHub"，而是**搬去私有载体**。这两件事必须一起决策，不能分开做。

### 事实 2：omn 崩溃 = 精确漏 1 件，不是"漏了一堆"

`logic/` 目录实读（CNB `nexus.zen/omn`）：

```
entrypoint.sh  gate.js  helper.sh  init-nim-keys.sh
omn_redact.py  omn_scheduler.py  package.json
policy-guard.js      ← 第 8 个业务文件，三处清单全都没它
tests/               ← 测试目录（运行时不需要）
```

而三处硬编码清单都只写了 **7 个业务文件 + flaretunnel = 8 项**：

| 位置 | 行 | 作用 |
|---|---|---|
| `space/start.sh` | **60–61** | boot 时拉哪些文件（还带 sha256 校验） |
| `.github/workflows/sync-logic-xnexus.yml` | **58–59** | CI 上传哪些文件 |
| `.github/workflows/sync-logic-xnexus.yml` | **104–105** | CI 读回校验哪些文件 |

`policy-guard.js` blob sha = `c155b012973b241533f63170903f104e942805fb`，与本地工作区文件**字节一致** → 权威源已确认。

`start.sh:52` 的注释写的是"拉 manifest + **9 件**（8 业务 + flaretunnel）"——**注释是对的，代码是错的**。这是典型的"文档正确、实现漏改"。

**为什么 CI 一直绿**：上传和校验用的是**同一份清单**，只验证"清单里的文件都对"，从不检查"清单本身全不全"。自我确认偏误 → 永远绿。

### 事实 3：镜像从未真正跑过（假绿），并且是一颗上弦的雷

**假绿机制**：`.cnb.yml` 里两处（push 触发 `:40-43`、crontab 触发 `:62-66`）都是

```sh
if [ -z "${GITHUB_TOKEN:-}" ]; then
  echo "⚠️ 未检测到 GITHUB_TOKEN，跳过本次镜像" >&2
  exit 0          # ← 退出码 0 = 构建显示"成功"
fi
```

缺 token 时**软跳过 + exit 0**，流水线显示绿色。近 5 天的 push 构建 + crontab 构建全是空转，从未推送过一次。

**两库已完全分叉**：

| | HEAD | 独有内容 |
|---|---|---|
| GitHub `i3t2y/nexus` | `4601942`（**09-07**） | `eval/` `hermes/` `mem0/` `other/` `README.md` `CONSTRAINTS.md` |
| CNB `nexus.zen/nexus` | `55c1b29`（**09-11**） | `logic/` `.cnb` `.cnb.yml` `.claude/` `CLAUDE.md` `tools/` `upstream/` `space/` `.gitmodules` |

**雷在哪**：`.cnb.yml:50` 是 `git push github HEAD:main --force`，**整树强推**。一旦配上 token，15 分钟内 GitHub 独有的一切（含 `eval/`）会被全部删除。

而 `.cnb.yml:23` 的注释自己写着：

> 使用 `--force` 是有意的（镜像语义）；**首次启用前请确认 GitHub 无 CNB 没有的独特提交**。

**——有，而且有一大堆。** 这句注释等于在按钮旁边贴了张"别按"，但没有任何机制阻止有人按。

### P2 · 河图结构性缺口（本次事故的真正教训）

**定性**：这次不是"AI 不听话"，是**系统里没有任何字段/角色/检查要求它做这件事**。靠"加强 AI 纪律"修不好，必须加硬约束。

| 缺口 | 现状 | 建议 |
|---|---|---|
| **G1** 无"部署影响面"字段 | 实验协议五字段只管测量，不问部署 | 加**第 6 字段「部署影响面」**：凡动 `logic/**` `space/**` `.github/workflows/**`，必须列受影响部署物 + 是否需人工重启；**空 = 拒收** |
| **G2** merge 原则覆盖不全 | `space/**`、`.github/workflows/**`、`logic/**` 增删**不在任何一行** | 分级表**加一行**：这三处 = **Zen 必审**（能改部署通路 ≈ 能自提权） |
| **G3** 闭环没有"上线"步 | idea→issue→PR→gate→merge→cases_pool，**止于 merge** | 加"部署动作 + 验证证据"回执，无回执 PR 不算关闭 |
| **G4** release-checklist 错位 | 它是"发布验收"表，不是"代码→部署物耦合"检查表 | 并入 G1，或单列 |
| **G5**（可选 · 治本） | 三处重复的清单，靠人肉同步 | 收敛为**单一 manifest 源**，由它生成 start.sh 与 workflow 的清单，从根上消灭"清单漂移" |
