### 一、基础设施与编排（Dockerfile / entrypoint.sh）

1. **镜像 Tag+Digest 双写锁定**——`FROM diegosouzapw/omniroute:3.8.43@sha256:517c160643c56ad72e3e305458d961c9a4c87f711393c13020450f9f088d1570`，digest 保证不可变（即使 Docker Hub tag 被覆盖也不会漂移），tag 便于人读和维护者快速识别版本，禁止浮动 `latest` 导致 3.8.45+ 的 Turbopack 构建漂移

6. **entrypoint 优雅降级 restore**——`litestream restore -config /litestream.yml -if-replica-exists "$DATA_DIR/storage.sqlite" && echo "restore complete." || echo "WARN: restore failed or no replica. Continuing."`，restore 成功就用恢复的库，restore 失败或 R2 无副本时空库继续启动，不阻断

### 二、安全网关（gate.js）

20. **gate.js 零依赖架构（v5/v4.3.1）**——纯 Node.js `http`/`fs`/`crypto` 内置模块实现反向代理，移除 express 和 http-proxy-middleware，彻底解决 better-sqlite3 和 node-gyp 在 Node 24 环境下的 C++20 编译冲突，显著降低镜像构建失败率和体积，Dockerfile 无需 `npm install`

21. **gate.js timing-safe PSK 比较（v4.3 candidate/in4.3）**——使用 `crypto.timingSafeEqual(Buffer.from(a), Buffer.from(b))` 常量时间比较，长度不等时先返回 false 不泄露 PSK 长度信息，长度相等时走常量时间比较，防止时序侧信道攻击

22. **gate.js PSK 最小长度 16 fail-closed（v4.3 candidate）**——`if (!INTERNAL_PSK || INTERNAL_PSK.length < 16) { process.exit(1); }`，缺失或过短即 FATAL exit，防止弱 PSK 配置导致安全降级

23. **gate.js 白名单暴露面控制（omn.md/in4.3）**——默认仅放行 `/healthz` 和 `/v1` + `/v1/*`，其余一律 404；路径判断用 `req.path === '/v1' || req.path.startsWith('/v1/')` 而非 `startsWith('/v1')`，防 `/v123` 或 `/v1admin` 绕过

25. **gate.js 路径规整化（v4.3 candidate）**——`normalizePath` 使用 `new URL(p, 'http://x')` 解析 dot-segment（`/v1/../api`）、重复斜杠（`//v1`）、尾斜杠（`/v1/`），防绕过白名单匹配

26. **gate.js PSK → OR_API_KEY 替换**——`/v1` 路径 PSK 校验通过后，`req.headers.authorization = 'Bearer ${OR_API_KEY}'`，客户端只需知道 PSK，Gate 负责替换为真实 OmniRoute 内部 API Key

28. **gate.js Authorization 删除（v4.3 candidate）**——Basic Auth 完成后 `delete req.headers.authorization`，不转发 Basic 凭据给上游 OmniRoute，防止凭据泄露

29. **gate.js SSE 流式超时全禁用**——`server.timeout = 0` / `server.requestTimeout = 0` / `server.headersTimeout = 0`（零依赖版）或 `proxyTimeout: 0` + `timeout: 0`（express 版），避免大上下文压缩期间（如 380K tokens 压缩需数秒）被网关掐断

30. **gate.js 流式超时感知（v5）**——SSE 请求（`Accept: text/event-stream` 或 GET `/v1/`）不设硬超时，非流式请求使用 `UPSTREAM_TIMEOUT_MS`，区分深度推理模型（GLM-5.1、DeepSeek R1）的 SSE 长连接与普通短请求

31. **gate.js 连接生命周期管理（v5）**——客户端断开时 `req.on('close')` 清理上游连接 `proxyReq.destroy()`，防 socket 句柄泄漏；在 HF Spaces 有限的连接池环境下至关重要，未清理的连接会累积导致端口耗尽

32. **gate.js SSE 逐块转发（v4.3 candidate）**——不聚合不 text/json 读流，`upstreamRes.on('data')` 逐块 pipe，`res.write(chunk)` 返回 false 时 `upstreamRes.pause()` + `res.once('drain', () => upstreamRes.resume())` 尊重背压

33. **gate.js HTTP 方法限制（v4.3 candidate）**——admin 页面仅允许 GET，admin API 按白名单允许方法（如 `/api/providers` 仅 GET），非允许方法返回 405 Method Not Allowed

42. **gate.js SIGTERM 优雅退出（v6）**——`process.on('SIGTERM', () => { server.close(() => process.exit(0)); })`，容器关闭时优雅关闭 HTTP 服务器，防连接泄漏；HF 平台重启容器时发送 SIGTERM

### 三、NIM Key 管理与初始化（init-nim-keys.sh）

45. **Cookie login 三重安全网（v4.3.1）**——接受 HTTP 200 或 201（`[ "$LOGIN_HTTP" != "200" ] && [ "$LOGIN_HTTP" != "201" ]`）+ `exit 1` 硬失败（login 失败立即退出不继续）+ `grep -q "auth_token" "$COOKIE_FILE"` 验证 cookie 有效，防 `set -eo pipefail` 在 jq 解析 401 响应时静默退出导致 25 Key 未注册

47. **NIM Keys 幂等注册**——409 状态码跳过已存在的 key（`elif [ "$HTTP_CODE" = "409" ]; then echo "exists"; SKIPPED=$((SKIPPED+1))`），脚本可安全重复执行，每次容器重启时已注册的 key 被跳过

48. **NIM Keys 规范化处理（omn.md）**——输入处理：删除 CRLF（`tr -d '\r'`）、去首尾空白（`xargs`）、删空行（`sed '/^[[:space:]]*$/d'`）、去重（`awk '!seen[$0]++'`）、只在内存处理、日志只显示序号和掩码（`nim-01 OK` 而非完整 key）、不进 HF Dataset 快照

49. **Key 输入校验**——`NIM_KEYS` 为空时 FATAL 但不阻塞主进程（`exit 0` 仅跳过注册），`INITIAL_PASSWORD` 为空时 `exit 1`（后续所有 API 调用都需要认证）

50. **init 双模式认证（v4.3.1）**——cookie login 用于 admin API 调用（provider 注册、Resilience PATCH、Settings PATCH 等）+ `OMNIROUTE_API_KEY` env-bypass 用于 Gate /v1 替换，两层独立，互不依赖

51. **init 同名连接更新而非仅 409 跳过（omn.md）**——存在时执行更新（PUT），而非只把 409 当作成功跳过，确保 key 的限流参数（RPM/concurrent/interval）始终与最新配置同步

52. **provider-nodes API fallback（新精简版）**——`/api/providers/{id}/connections` 失败时 fallback `/api/provider-nodes`，兼容不同 OmniRoute 版本的 API 路径差异

### 四、限流策略

57. **线性扩容公式（v4.2.3）**——`_RPM=$(( _ALIVE_KEYS * _PER_KEY_RPM ))`（25×35=875→截 300）+ `_CONCURRENT=$(( _ALIVE_KEYS * 3 ))`（25×3=75）+ `_MIN_INTERVAL_MS=$(( 60000 / _RPM ))`（60000/300=200ms），25 Key 下高并发容差充足

58. **保守整形策略（v4.3/in4.3）**——默认固定 28 RPM / 1 并发 / 2200ms，通过"整形"而非"扩容"显著降低 429 熔断率；NIM 免费层对瞬时并发极其敏感，28 RPM 留出 30% 安全余量（NIM 限速约 40 RPM）

59. **CONSERVATIVE / SCALE 限流可切换（新精简版）**——`NIM_SCALE_WITH_KEYS=1` 切换线性扩容，默认保守模式 28/1，环境变量控制无需改代码

60. **删除 NIM_SCALE_WITH_KEYS（in4.3）**——即便默认设为 0，仍会给维护者留下"Key 可线性扩容"的错误暗示；多 Key 仅作冗余与健康轮换，不叠加吞吐

61. **Resilience 白名单投影（v4.3.1）**——请求体只含 `requestQueue`（`requestsPerMinute` / `minTimeBetweenRequestsMs` / `concurrentRequests`），不含 `useUpstream429BreakerHints`，从根源修复 OmniRoute 3.8.43 API 返回 400 `Unrecognized key` 的错误

62. **Resilience 传输错误区分（v4.3.1）**——`curl_rc != 0` 或 `RESILIENCE_CODE` 为空时判定为 transport-error（非 HTTP 错误），区分"无响应异常"（连接拒绝/超时）与"HTTP 非 2xx"（400/500），分别记录不同日志

63. **Resilience 读回逐字段核对（v4.3.1）**——PATCH 后立即 GET `/api/resilience` 读回 RPM / minMs / concurrent，逐字段与预期比对：`_RB_RPM != $_RPM` 则 `_mismatch="RPM($_RB_RPM!=$_RPM)"`，不一致 `exit 1`（CF-4 失败不覆盖的强化版）

64. **Resilience 输入校验（v4.3.1）**——`_res_validate_int` 在 PATCH 前校验 RPM(1-60000) / minMs(0-600000) / concurrent(1-1000) 范围，非法值直接 `exit 1` 不发送请求

65. **Resilience 能力发现模式（omn.md）**——先 GET 候选端点（`/api/resilience`），只对返回 2xx 且结构符合预期的端点写入，写入后再次 GET 读回验证，不支持的层记录 `unsupported` 不操作 SQLite

66. **删除 Resilience 猜测字段（in4.3）**——彻底删除 `providerBreaker` / `connectionCooldown` 猜测字段；官方 RESILIENCE_GUIDE.md 证实熔断仅对 408/500/502/503/504 触发不含 429——429 归 Connection Cooldown 管（尊重 `Retry-After`）

67. **jq 引号 BUG 修复（v4.3.1）**——变量预取 `_sent_keys=$(echo "$RESILIENCE_BODY" | jq -rc 'keys | join(",")')` 替代 `'"'"'` 堆叠，消除 jq 引号转义错误

68. **Gate 内存令牌桶不依赖 OmniRoute API（in4.3）**——Gate 自行强制执行共享预算，不依赖 OmniRoute 内部 Request Queue API（其 Schema 未完全锁定），即使 OmniRoute 的 Resilience API 不可用或字段变更，Gate 限流仍然生效

69. **限流参数硬上限保护**——`[ "$_RPM" -gt 300 ] && _RPM=300`（RPM 不超过 300）、`[ "$_CONCURRENT" -lt 3 ] && _CONCURRENT=3`（并发至少 3）、`[ "$_REQUEST_BODY_LIMIT_MB" -gt 500 ] && _REQUEST_BODY_LIMIT_MB=500`（body 不超过 500MB）
